# AUDIT CX — AgentB2C avant exposition client (2026-07-24)

Audit demandé par Fabien avant l'exposition du concierge aux clients finaux. Deux axes :
**(1) zéro fuite d'erreur** vers le client, **(2) interactivité proactive** (qualification des
demandes + propositions, notamment autour du budget/prix plancher du client).

**Méthode** : lecture de code exhaustive des surfaces client (façade `/v3/*`, spine concierge,
feuilles, guards, templates) + **passe de vérification live** (stack locale 3 services, MCP
staging réel, LLM réel) : 10 sondes inoffensives + 4 scénarios destructifs (feuille tuée,
MCP coupé, synthèse cassée, crash inattendu reproduit in-process). Chaque constat est tagué
**[LIVE]** (reproduit sur la stack), **[CODE]** (prouvé par lecture, file:line) ou
**[HYPOTHÈSE]**. Aucun code produit n'a été modifié — rapport seul, les fixes partent en
sessions dédiées après GO.

---

## Résumé exécutif

**Le socle est bon.** La discipline « dégradation honnête » du spine est réelle et vérifiée
live : feuille morte → template français propre en 1,2 s ; body malformé → ack ; session
invalide → 400 JSON propre sur les 3 routes ; Redis/DB down → tour normal ; debug off partout
(aucune trace de stack possible) ; les métriques ne touchent jamais le payload. La majorité du
travail « anti-fuite » est déjà faite et testée.

**Mais 3 trous P0 subsistent avant d'exposer des clients**, tous reproduits :

| # | Constat | Ce que le client voit | Preuve |
|---|---|---|---|
| F1 | La façade n'a **aucun bouclier d'exception** ; le SSE n'a **pas d'événement `error`** | JSON : `500 Internal Server Error` texte brut hors contrat. SSE : flux mort sans `done` — le widget ne peut pas distinguer « réfléchit » de « planté » | [LIVE in-process] |
| F2 | MCP injoignable → **fausse rareté** : le breaker ne voit pas l'échec d'énumération du toolset, le modèle conclut « pas d'offres » | « Il n'y a pas d'offres de jour à Marseille pour demain » — **faux** (le backend était mort), perte de vente + mensonge factuel, reproduit 4/4 | [LIVE] |
| F3 | Synthèse en échec → **texte machine anglais verbatim** à un client français, `response_language` incohérent ; le jargon circuit-breaker peut passer par ce chemin | `"5 day-use offer(s) found: Villa Paris Orly, …"` avec `response_language: "fr"` | [LIVE] |

**Sur l'interactivité, le verdict est structurel** : l'agent est honnête mais passif. Il ne
propose jamais rien de concret — le cas budget est le plus parlant : « max 10 € à Paris » →
« augmentez votre budget » générique, sans jamais dire *« la moins chère est à 54 € »*, parce
que **le code n'a littéralement pas la donnée** (filtre prix dur côté MCP + prix numérique
perdu sur les cartes). La mise en avant pondérée scoring × proximité budget demandée par
Fabien nécessite de débloquer ces deux points d'abord (recommandation R4).

## Axe 1 — Fuites d'erreur et robustesse des chemins d'échec

### F1 — P0 · La façade n'a aucun handler d'exception de dernier recours [LIVE in-process + CODE]

`chat()` (`facade.py:690-704`) et le générateur SSE `_body()` (`facade.py:731-761`) pilotent
`_drive`/`_finalize` sans try/except. Tout ce qui est *à l'intérieur* du spine est protégé
(triage, feuille, synthèse, Redis) — mais les coutures de la façade elle-même ne le sont pas :
`_apply_native_context` → reducers de profil, construction du router LiteLLM, internals du
runner ADK, ou n'importe quel bug imprévu.

Reproduit in-process (app ASGI réelle `serve.app`, `_drive` patché pour lever) :

- **JSON** : `HTTP 500`, `content-type: text/plain`, body exactement `Internal Server Error`,
  pas de cookie de session. Le widget qui parse le contrat JSON n'a **aucun champ `message`**
  à afficher.
- **SSE** : le `200` + `text/event-stream` sont déjà commis quand le générateur démarre — une
  exception mid-stream tue la connexion **sans frame `done` et sans frame `error`** (aucun
  événement `error` n'existe dans le code ; les seuls events sont `progress`/`hotels`/`token`/
  `done`). L'EventSource client voit une connexion coupée, indistinguable d'un réseau lent.

Atténuation existante : debug off partout (pas de `debug=True`, pas de `--reload`), donc jamais
de traceback rendu — la fuite est un 500 nu / un flux mort, pas du code source. Aucun test ne
couvre ces chemins (`tests/api/` ne teste que succès + auth + session invalide + ack).

### F2 — P0 · MCP injoignable → fausse indisponibilité présentée comme un fait [LIVE]

Scénario : feuille search redémarrée avec `MCP_B2C_URL` pointant sur un port mort, 4 recherches
« hôtel à Marseille demain » successives. Résultat **4/4** :

> « Je suis désolé, mais il n'y a pas d'offres de jour à Marseille pour demain. Vous pourriez
> envisager de changer la date, d'élargir la zone ou d'ajuster votre budget. »

Aucun jargon ne fuit (bien) — mais c'est un **mensonge factuel** : Dayuse a de l'inventaire à
Marseille, c'est le backend qui était mort. Le client repart en croyant qu'il n'y a pas d'offre
(vente perdue), et les métriques comptent un « 0 résultat » légitime.

Root cause (logs feuille) : avec le serveur MCP injoignable, c'est l'**énumération du toolset
MCP** qui échoue (`Error on session runner task: unhandled errors in a TaskGroup`) —
`search_offers` n'est **jamais appelé** (seul `geocode_location`, tool local, tourne). Le
circuit-breaker (`mcp_guard.py`) ne voit donc rien passer : il ne protège que l'échec d'un
*appel* de tool, pas l'absence du tool. Le modèle feuille, sans résultat ni diagnostic
d'échec, improvise « pas d'offres » et `emit_search_datapart` ne se déclenche pas — le
concierge synthétise ça comme un vrai zéro.

À noter : le chemin « feuille complètement morte » (process tué) est lui **parfait** [LIVE] :
template honnête « Je n'arrive pas à joindre la recherche d'hôtels pour le moment, et je
préfère ne rien inventer. Pouvez-vous réessayer dans un instant ? », 200, 1,2 s. C'est
l'asymétrie qui est le bug : *feuille morte = honnête, dépendance de la feuille morte = mensonge*.

### F3 — P0 · Synthèse en échec → texte feuille anglais verbatim + jargon possible [LIVE + CODE]

`agent.py:911` : `final_text = synth or leaf_text or templates.leaf_degraded_response(...)`.
Reproduit live (concierge relancé avec un modèle de synthèse invalide, triage retombé sur le
fallback regex, feuille saine) — un client français demandant « un hôtel à Paris demain »
reçoit :

> `5 day-use offer(s) found: Villa Paris Orly, OKKO Hotels Paris Rueil Malmaison, Eurohotel
> Créteil, Novotel Paris La Défense Nanterre, Campanile Prime Paris Porte d'Italie.`

…avec `response_language: "fr"` dans le payload (le widget qui s'y fie affiche de l'anglais
sous une étiquette fr). Source : `_outcome_text` hardcodé anglais
(`response_bridge.py:727-746`), question de clarify géo idem (`geo_resolver.py:161-171`).

**Aggravation [CODE]** : sur ce même chemin verbatim, si la feuille a subi un échec MCP en
circuit ouvert, le modèle feuille reçoit
`"reason": "MCP_B2C unavailable — circuit open after repeated failures"` (`mcp_guard.py:26-34`)
et son instruction lui demande de « relayer les diagnostics honnêtement » — le jargon
(`MCP_B2C`, `circuit`, `geocode`) peut donc devenir le texte final si la synthèse échoue en
même temps. Double panne improbable, mais la chaîne existe et rien ne filtre ces tokens.

### F4 — P1 · Aucune limite de taille de message, pas de rate limiting [LIVE + CODE]

Un message de **300 Ko** est accepté et traité de bout en bout (18,8 s, 200, le garbage part
dans les appels LLM — ~75 k tokens facturés sur le tour). Aucun cap, aucun 413, aucune
troncature (`facade.py` : `message` passé tel quel au spine), aucun rate limiting sur les
routes `/v3/*`. Surface coût/DoS réelle une fois l'endpoint public, même derrière un BFF.

### F5 — P1 · Localisation incohérente des textes de secours [LIVE + CODE]

- Fallback verbatim anglais (F3).
- Ack localisé par `guess_language(message)` seulement : un premier message « ok » ou un body
  malformé sans `locale` → salutation **anglaise** pour un client français [LIVE, P1-P3].
  (`_empty_ack_text` `facade.py:657-662` accepte pourtant déjà la locale — elle n'est juste
  pas toujours fournie/utilisée sur les autres chemins d'ack, `agent.py:775`.)
- Les templates dégradés, eux, sont correctement bilingues partout (`templates.py`, via `_pick`).

### F6 — P2 · Gaps de couverture de tests sur les chemins client [CODE, vérifié live]

- Les 400 sur `/v3/chat/stream` et `/v3/chat/session/reset` sont **corrects live** (vérifiés
  ce jour) mais non testés en CI.
- Aucun test façade HTTP des chemins de dégradation réels (feuille down, synthèse down, Redis
  down à travers la vraie façade) — ils sont testés au niveau unitaire spine seulement.
- Shapes d'erreur incohérentes : façade `{"error": ...}` vs gate A2A `{"detail": ...}`
  (`auth.py:56`) — interne, mais à normaliser.

### ✅ Ce qui est déjà solide (ne pas reconstruire)

Vérifié live et/ou verrouillé par tests : dégradation feuille morte (template fr/en, testé
`test_spine.py:318`) ; triage LLM down → fallback regex (`triage.py:166-179`) ; Redis down →
profil vide + write no-op (`profile_store.py:41-69`) ; DB logs down → warning avalé ; body
malformé/non-dict/vide → ack 200 ; retry synthèse borné par type d'exception
(`test_synthesis_retry_policy.py`) ; guards link/amenity silencieux et testés ; ordre SSE
`progress → hotels → token → done` verrouillé + TTFT progress-first ; métriques/GPS jamais
dans le payload (verrouillé RGPD) ; debug/traceback impossible.

## Axe 2 — Interactivité : qualification et propositions

### État des lieux [CODE + LIVE]

L'agent ne pose une question ou ne fait une proposition que dans 5 situations : salutation
(demande ville+date), homonyme géo (clarify déterministe), booking (confirmation/choix),
0-résultat (générique « changez la date, élargissez la zone, ajustez le budget » + chips
`suggestions`), échec feuille (« réessayez »).

Nuance découverte live (P8) : « je veux un hôtel » reçoit bien *« pourriez-vous préciser la
ville ou la région ? »* — la qualification **ville** existe de facto, portée par le LLM feuille
(il ne peut pas géocoder sans lieu). Mais elle n'est ni déterministe, ni structurée :
`requires_clarification` reste `false` (le widget ne sait pas qu'une question est posée), et
rien n'existe pour date, budget, durée, équipements — le spine est search-first par design
(triage sans intent « browse », `FALLBACK_FAMILY = "search"`, la feuille documente « un
argument omis = pas de contrainte »).

### G1 — Le cas budget est un dead-end sans proposition [LIVE]

« hôtel à Paris demain, budget max 10 € » →

> « Il n'y a pas d'offres de jour disponibles à Paris pour demain avec un budget maximum de
> 10 €. Je vous recommande d'augmenter votre budget, de changer de date ou d'élargir la zone… »

Honnête, mais l'agent ne dit jamais *« la moins chère est à 54 € — je vous la montre ? »*.
Trois blocages structurels [CODE] :

1. **`priceRangeMax` est un filtre dur côté MCP** : les hôtels hors budget ne sont jamais
   renvoyés — le code n'a pas la donnée pour proposer le plus proche au-dessus.
2. **Le prix numérique est perdu sur la carte** : `normalize_hotel` ne garde que
   `price = "€X.XX"` formaté (`response_bridge.py:458-462`) ; aucune logique prix code-owned
   n'est possible côté concierge sans re-parser une string.
3. **`maybe_auto_widen` ne s'applique jamais à un budget explicite** (`profile.py:277-281`) —
   choix sain (ne jamais écraser le client) mais rien ne le remplace par une *proposition*.
   Et quand il s'applique (budget implicite), il est silencieux : appliqué *pour* le client,
   jamais proposé *au* client.

### G2 — Aucune mise en avant : ni tri prix, ni pondération scoring [CODE]

La shortlist (cap 5) sort dans l'ordre MCP. Le seul traitement prix est `_best_offer` =
offre la moins chère *par hôtel* (`response_bridge.py:374-378`) ; il n'existe **aucun
re-ranking cross-hôtels** — ni par prix, ni le blend **scoring (rating) × proximité au budget
client** souhaité par Fabien. Les données nécessaires existent pourtant par carte : `rating`,
`stars`, `distance_km`, et `priceEuro` (à condition de le préserver en numérique, cf. G1.2).

### G3 — Zones voisines et dates alternatives jamais concrètes [CODE]

L'élargissement métro se fait silencieusement dans le resolver géo ; les « autres dates » ne
sont suggérées qu'en générique. Jamais de « rien à X, mais Y à 3 km a 4 offres » ni de date
concrète testée. (Proposition de date concrète = un probe MCP supplémentaire — à dimensionner
face au budget d'appels.)

### Contraintes non négociables pour tout fix (héritées du spine)

≤ 3 appels LLM/tour (`budget.py:18`) ; guards one-shot, jamais de re-loop ; anti-boucle de
clarification (`profile.py:700-722`) ; `MAX_TOOL_CALLS=2` côté feuille ; un budget explicite
n'est jamais écrasé silencieusement ; **le LLM ne possède jamais une valeur de filtre/prix**
(le code calcule, le LLM formule) ; les évals `budget_change`/`zone_change` exigent
`requires_clarification == false` sur les tours de raffinement → toute nouvelle question doit
être scopée au 1er tour réellement vague.

## Recommandations (priorisées)

**R1 — P0 · Bouclier façade + signal SSE terminal garanti.** try/except de dernier recours
autour de `chat()` et du générateur `_body()` : payload iso-contrat avec message dégradé
honnête (réutiliser `templates.leaf_degraded_response`) au lieu du 500 nu ; côté SSE, un
`try/finally` garantissant TOUJOURS une frame terminale. Décision de contrat à prendre avec le
widget : nouvelle frame `error` (plus propre, mais le widget doit l'implémenter) ou `done`
dégradé (zéro changement widget). Tests façade des deux chemins. Petit chantier, très contenu.

**R2 — P0 · Vérité d'indisponibilité (MCP down ≠ 0 résultat).** La feuille doit détecter
« l'outil de recherche n'était pas disponible ce tour » (énumération toolset échouée OU
circuit ouvert) et l'émettre en DataPart (`status=tool_unavailable`) → le concierge route vers
le template dégradé honnête au lieu de synthétiser une fausse rareté. Neutraliser au passage le
`reason` du circuit-breaker (`mcp_guard.py`) en texte client-neutre sans « MCP_B2C/circuit ».
C'est le fix qui protège le chiffre d'affaires (fausse rareté = vente perdue en silence).

**R3 — P1 · Fallbacks localisés et cohérents.** Quand la synthèse échoue : si le tour feuille
a échoué, préférer le template dégradé localisé au `leaf_text` brut ; sinon, localiser
`_outcome_text` et la question de clarify (fr/en, via `profile.language` — même périmètre
fr/en qu'aujourd'hui, pas d'i18n élargie). Garantir `response_language` = langue du texte
réellement servi. Ack : utiliser la locale du profil avant `guess_language`.

**R4 — P1 · Chaîne « prix plancher » (la demande produit de Fabien).** Quatre pièces, dans
l'ordre, toutes code-owned :
  a. Préserver `price_eur_cents` numérique sur la carte (1 ligne dans `normalize_hotel` +
     miroir `inline_tools`).
  b. Fallback hors budget côté feuille : quand un budget **explicite** donne 0, re-probe sans
     `priceRangeMax` (précédent exact : fallback timeslot `response_bridge.py:633-642`) et
     disclosure honnête — le budget du client n'est jamais écrasé, on lui *montre* l'écart.
  c. **Re-ranking blend de la shortlist : pondération scoring (rating) × proximité du prix au
     budget client** — en code dans le concierge, valeurs jamais possédées par le LLM ;
     formule simple à calibrer (ex. `w1·rating_norm + w2·(1 − |prix−budget|/budget)`), à
     valider sur l'eval ranking (Gate 7, débloqué en S-G10).
  d. Template/note déterministe de proposition : « La moins chère est à 54 € (44 € au-dessus
     de votre budget) — je vous montre les 3 plus proches de votre budget ? » — même mécanique
     que `widen_note`/`currency_note`.

**R5 — P1 · Qualification structurée.** (a) Quand la feuille pose une question de
qualification (ville manquante), propager `requires_clarification=true` (le canal existe déjà
pour le clarify géo) pour que le widget puisse afficher une UI de question. (b) Chips
`suggestions` contextuelles au lieu des 3 chips fixes (ex. proposer des créneaux/équipements
quand la shortlist est large et sans filtre). (c) Optionnel, à trancher : règle de synthèse
« terminer par UNE question de qualification quand la shortlist est large et sans filtre
budget/heure » — scopée pour ne pas régresser l'anti-boucle ni les évals.

**R6 — P2 · Durcissement périmétrique.** Cap de taille sur `message` (ex. 4 000 caractères,
413 ou troncature honnête), rate limiting (peut vivre au BFF — à confirmer avec l'équipe
widget), tests façade des chemins dégradés (F6), normalisation des shapes d'erreur.

### Roadmap proposée (une session = un scope)

| Session | Contenu | Fixes |
|---|---|---|
| S-CX1 | Bouclier façade + frame SSE terminale + tests | R1 |
| S-CX2 | Vérité MCP-down bout-en-bout + jargon neutralisé + fallbacks localisés | R2, R3 |
| S-CX3 | Chaîne prix plancher (carte numérique → fallback → blend ranking → proposition) | R4 |
| S-CX4 | Qualification structurée + chips contextuelles + caps/rate limiting | R5, R6 |

S-CX1 et S-CX2 sont bloquantes avant toute exposition client réelle ; S-CX3/S-CX4 sont la
valeur produit demandée (interactivité) et peuvent suivre en canary.
