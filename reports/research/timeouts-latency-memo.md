# Memo: Timeout, retry, and hedging architecture for the AgentB2C leaf-call path

> Research memo — 2026-07-23. Input for `reports/PLAN-RESOLUTION-GEO-MULTITURN-2026-07-23.md`.
> All claims verified against primary sources except where flagged at the end.

Context: fixed 10 s leaf-call timeout (no retry) is below observed tail latency (p50 turn 9.8 s, p95 26.7 s), causing technical degradations on cold starts, long FAQ syntheses, and one pathological city. Research below covers (a) timeout architecture, (b) LiteLLM capabilities, (c) hedging applicability, (d) ADK/A2A specifics and streaming UX.

## (a) Recommended timeout architecture patterns

**1. Deadline propagation, not independent per-hop timeouts.** The Google SRE book ([Addressing Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/)) is explicit: set one absolute deadline high in the stack (the facade/turn level) and propagate the *remaining* budget down each hop — "If server A selects a 30-second deadline and processes for 7 seconds before calling server B, the RPC to B has a 23-second deadline." Each phase spends from a shared turn budget instead of every hop owning a fixed 10 s. gRPC formalizes this ([gRPC deadlines](https://grpc.io/blog/deadlines/)): "always set a deadline", servers check remaining deadline before doing expensive work, and cancellation is propagated so a doomed leaf stops calling Mapbox/MCP once the orchestrator has given up. For the A2A/HTTP stack, the equivalent is passing a `deadline` or `remaining_ms` field in the A2A `DataPart`/metadata and having the leaf check it before each phase.

**2. Set the timeout from a target false-timeout rate, not intuition.** The Amazon Builders' Library ([Timeouts, retries, and backoff with jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/), Marc Brooker) gives the standard procedure: choose an acceptable false-timeout rate (e.g. 0.1%), then set the timeout at that latency percentile of the *healthy* downstream (p99.9 for 0.1%). The 10 s deadline sits below the observed tail of legitimate work (long FAQ syntheses), i.e. it deliberately times out a large fraction of *correct* requests — the audit finding is the predicted failure mode of a timeout set under the healthy tail. Corollary: Chester GB timing out "even in isolation" is not a timeout problem; it is the SRE book's **bimodal latency** case (a request class that never completes) — fix the root cause in the leaf, don't widen the deadline for it.

**3. Per-phase budgets inside the leaf, single global deadline outside.** These compose: the orchestrator propagates one turn deadline; inside the leaf, each dependency keeps its own cap (Mapbox 1.5 s, MCP 5 s — already in place) *and* is additionally clipped by the remaining propagated budget. This preserves the "one owner per dependency" invariant while eliminating the arbitrary mid-pipeline 10 s wall.

**4. Adaptive/percentile-driven timeouts.** A 2026 InfoQ piece ([Adaptive hedged requests](https://www.infoq.com/articles/adaptive-hedged-requests-p99-latency/), May 2026) shows the production-grade version: learn the live latency distribution (DDSketch quantile sketch, 30 s tumbling windows) and derive the trigger threshold (their hedge fired at per-host p90; result: p99 65 ms → 17.3 ms, +8.9% load). A lighter static version is enough here: derive the leaf deadline per intent class (search vs FAQ) from observed healthy percentiles, revisited from metrics — FAQ synthesis legitimately needs a longer budget than search.

**5. Retry rules (SRE book):** jittered exponential backoff always; per-request retry cap (≤3 attempts); a server-wide retry *budget* (e.g. 60 retries/min per process, fail beyond it); and **retry at one layer only** — retries at N layers multiply into attempt^N amplification ("a single user action may create 64 attempts (4^3)"). The existing invariant "retries LLM au seul niveau LiteLLM" is exactly this rule; keep the orchestrator→leaf hop at 0 retries and let LiteLLM own LLM-level retries.

## (b) LiteLLM retry/timeout/fallback capabilities (verified parameter names)

SDK-level ([Reliability - Retries, Fallbacks](https://docs.litellm.ai/docs/completion/reliable_completions)):
- `completion(..., num_retries=2)` — retries via tenacity.
- `completion(..., fallbacks=["gpt-3.5-turbo", ...])` and `context_window_fallback_dict={...}`; fallback entries can also swap `api_key`/`api_base` dicts.

Router-level ([Router - Load Balancing](https://docs.litellm.ai/docs/routing)):
- `num_retries`, `retry_after` (min seconds before retry), and a `RetryPolicy` class with **per-exception retry counts** (`TimeoutErrorRetries`, `RateLimitErrorRetries`, `BadRequestErrorRetries`, `AuthenticationErrorRetries`, `ContentPolicyViolationErrorRetries`) — lets you retry timeouts once but never retry 400s.
- Per-deployment `litellm_params`: `timeout` (complete response) and `stream_timeout` (**time to first chunk** — directly protects the <300 ms TTFT SLO on the synthesis stream; [Timeouts](https://docs.litellm.ai/docs/proxy/timeout)).
- Built-in circuit-breaker-like **cooldowns**: `allowed_fails` (default 3/min), `cooldown_time` (default 5 s), `disable_cooldowns`, per-exception `AllowedFailsPolicy`; deployments auto-cool-down on 429s or >50% failure rate in the current minute.
- Fallback chains ([Fallbacks](https://docs.litellm.ai/docs/proxy/reliability)): `fallbacks`, `default_fallbacks`, `context_window_fallbacks`, `content_policy_fallbacks`; per-request `"disable_fallbacks": true`.
- Per-request overrides: `timeout` in the request body / `extra_body`, and proxy headers `x-litellm-timeout`, `x-litellm-stream-timeout`, `x-litellm-num-retries` ([Request Headers](https://docs.litellm.ai/docs/proxy/request_headers)) — this is the natural carrier for **deadline propagation into the LLM layer**: compute remaining turn budget, pass it as the per-request `timeout`.

## (c) Hedging applicability to non-idempotent LLM calls

- Canonical source: Dean & Barroso, [The Tail at Scale](https://www.barroso.org/publications/TheTailAtScale.pdf) — hedge after the p95 of expected latency; Google cut p99.9 from 1800 ms to 74 ms with only ~2% extra requests. Tied requests (cross-cancellation) reduce the duplicate work further.
- gRPC's formal position ([Request Hedging guide](https://grpc.io/docs/guides/request-hedging/), [proposal A6](https://github.com/grpc/proposal/blob/master/A6-client-retries.md)): `hedgingPolicy` (`maxAttempts` ≤5, `hedgingDelay`, `nonFatalStatusCodes`) is mutually exclusive with `retryPolicy`, and "only idempotent methods should specify a hedging policy."
- For LLM calls specifically: a pure completion call is **side-effect-free at the provider** (read-like), so hedging is *semantically* safe — the duplicate cost is tokens, not corrupted state. It becomes unsafe when the LLM turn *triggers tools with side effects* (booking-link generation, writes) or when responses are non-deterministic in a way that matters downstream (two hedged triage calls could classify differently; you must commit to exactly one winner and cancel/discard the loser). Cautions from [InfoQ](https://www.infoq.com/articles/adaptive-hedged-requests-p99-latency/) and practitioner material: don't hedge into rate limits (hedges burn quota), don't hedge single-backend/CPU-saturated services, and either hedge only idempotent operations or deduplicate (idempotency keys / result caching).
- **Applied to AgentB2C:** hedging the whole leaf call duplicates its Mapbox + MCP fan-out (read-only ES, so idempotent, but 2x load) and its LLM extraction call — which collides with the hard ≤3 LLM calls/turn budget. The defensible scope is narrow: hedge only the cheap triage call, or prefer LiteLLM `fallbacks` (sequential failover after `stream_timeout`, cheaper than parallel hedging) over true hedging. R9-gated `generate_booking_link` must never be reachable from a hedged/retried path.

## (d) ADK / A2A specifics and streaming UX

- **`RemoteA2aAgent`** (verified in [adk-python source](https://github.com/google/adk-python/blob/main/src/google/adk/agents/remote_a2a_agent.py)): constructor takes `timeout: float = DEFAULT_TIMEOUT` where `DEFAULT_TIMEOUT = 600.0` seconds, applied as `httpx.Timeout` on the shared `httpx.AsyncClient` covering both agent-card resolution and message send. `httpx_client` is accepted but marked deprecated in favor of `a2a_client_factory`. So ADK gives you one blunt per-agent HTTP timeout — per-turn deadline propagation must be application-level (pass remaining budget in the A2A payload), which matches the gRPC-style pattern above. There is no documented per-call deadline API on `RemoteA2aAgent`.
- **A2A protocol** ([Streaming & Asynchronous Operations](https://a2a-protocol.org/latest/topics/streaming-and-async/)): built for long-running tasks — SSE `TaskStatusUpdateEvent` progress updates, partial results, `final: true` terminal marker, `tasks/resubscribe` after connection loss, and push-notification webhooks for very long tasks. If a leaf legitimately needs >10 s (FAQ synthesis), the protocol-idiomatic answer is the leaf streaming status/partials rather than the orchestrator blocking on a unary call.
- **Cold starts**: Cloud Run guidance ([min-instances docs](https://docs.cloud.google.com/run/docs/configuring/min-instances), [3 ways to optimize Cloud Run response times](https://cloud.google.com/blog/topics/developers-practitioners/3-ways-optimize-cloud-run-response-times), [startup CPU boost](https://cloud.google.com/blog/products/serverless/announcing-startup-cpu-boost-for-cloud-run--cloud-functions)) — min-instances ≥1 (already mandated), startup CPU boost, and measuring `container/startup_latency` before sizing. Google's [Agent Engine scaling docs](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/optimize-and-scale) confirm ADK agents behave best under stable warm load. Note: min-instances keeps the *container* warm, not the first LLM call — provider-side cold latency (first LiteLLM call after idle) is only mitigated by a synthetic warm-up ping or by budgeting the first-call tail into the deadline.
- **Streaming UX** ([Redis: Streaming LLM responses](https://redis.io/blog/streaming-llm-responses/), [Boundev: loading/error states](https://www.boundev.ai/blog/ai-feature-loading-error-empty-states-ux)): streaming cuts *perceived* wait 55–70% at identical wall-clock; users tolerate 10 s+ if a status line keeps updating ("Searching hotels near X…" → "Comparing offers…"), but abandon a static screen in 2–3 s. The <300 ms `progress` event plus the `hotels` partial event is the right shape — the mitigation for a slow leaf is *more intermediate status events during the wait* (relay the leaf's A2A status updates as SSE progress events), not a tighter timeout.

## Concrete synthesis for AgentB2C

1. Replace the single 10 s wall with a propagated turn deadline (facade-owned, e.g. derived from healthy p99 per intent class), passed to the leaf in the A2A payload and to LiteLLM via per-request `timeout`; keep per-dependency caps (Mapbox 1.5 s, MCP 5 s) as local minima of (own cap, remaining budget).
2. Keep 0 retries at the orchestrator→leaf hop (SRE anti-amplification rule); express LLM retries as a LiteLLM `RetryPolicy` (retry `TimeoutError`/`RateLimitError` once, never `BadRequestError`) plus `stream_timeout` to protect TTFT, and cooldowns (`allowed_fails`/`cooldown_time`) as the circuit breaker.
3. Treat hedging as out of scope for now (LLM-call budget + cost); if ever needed, hedge only the triage call with a p95-based hedge delay and strict winner-commit.
4. Fix Chester GB as a correctness bug (bimodal latency class), independently of any timeout change.

## Not verified / flags

- The claimed "55–70% perceived-wait reduction" comes from vendor blog user testing (Redis/Boundev), not peer-reviewed work.
- No *official* ADK documentation page found for per-call (per-invocation) timeouts on `RemoteA2aAgent` — only the constructor-level `timeout` verified in source; treat per-turn deadlines as necessarily application-level.
- A dev.to article on LiteLLM failover adding 30+ s latency (default-timeout × retry × cooldown interplay) returned 404; the failure mode is plausible (default timeouts are long, and router `timeout` covers the entire call including retries per the docs) but that specific write-up is unverified.
- LiteLLM docs state router `timeout` "is for the entire length of the call" (i.e., includes retries) — verified in [routing docs](https://docs.litellm.ai/docs/routing), but not tested whether `num_retries` attempts each get the full timeout or share it; worth a 10-line local test before relying on it.
